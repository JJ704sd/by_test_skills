# Triage

If tracker or label conventions are missing, run `$configure-engineering-skills` first. Include external PRs only when `docs/agents/issue-tracker.md` marks them as a request surface.

Prefix every posted issue, PR, or comment with:

```text
> *This was generated by AI during triage.*
```

Assign exactly one configured category role (`bug` or `enhancement`) and one state role (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`). Resolve actual labels through `docs/agents/triage-labels.md`; stop for missing or conflicting mappings, and treat unusual transitions as recommendations until confirmed.

For discovery, show oldest-first unlabeled inbound items, `needs-triage` items, and `needs-info` items with new reporter activity. When external PRs are enabled, discover only non-maintainer PRs, label results `[issue]` or `[PR]`, and always allow an explicitly named PR.

## Triage one item

1. Read the full item, history, metadata, and PR diff when applicable. Explore relevant code and domain docs, search for an existing implementation, then use the [out-of-scope workflow](references/out-of-scope.md) to check prior rejections.
2. Recommend category and state with evidence, including where redundancy was checked. Wait for maintainer direction.
3. Verify only whether the inbound claim is credible before interviewing: reproduce the reported symptom, or check out and test a PR's stated behavior. Do not expand triage into a complete Standards/Spec review; use `$review-code-against-spec` only when that review is separately requested. Report confirmed, failed, or insufficient evidence.
4. If human-owned decisions remain, use `$elicit-stakeholder-input` live mode; add `$domain-modeling` only when settled vocabulary or an ADR should persist.
5. Apply the confirmed outcome:
   - `ready-for-agent` or `ready-for-human`: follow the [brief rules](references/agent-brief.md) and use the [brief template](assets/agent-brief-template.md); state why human work is required when applicable.
   - `needs-info`: use the [needs-info template](assets/needs-info-template.md).
   - `wontfix`: distinguish already implemented, rejected bug, and rejected enhancement; only rejected enhancements update `.out-of-scope/`.
   - `needs-triage`: apply the role, with an optional progress comment.

For a direct maintainer override, preview the label, comment, and close actions, then apply only the confirmed change; ask whether a brief is wanted when moving directly to `ready-for-agent`. On resumption, rebuild state from prior notes and replies and never re-ask resolved questions. Stop after reporting the confirmed state and performed actions; do not implement the request.
