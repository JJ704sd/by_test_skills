## 质量原则

- **完整**：覆盖需求、正常/异常/边界、错误恢复和关键兼容组合。
- **准确**：预期结果与已确认的业务规则、契约或指标一致。
- **可执行**：前置条件、数据、步骤和环境无隐含依赖。
- **独立**：尽量避免用例间顺序依赖；需要共享状态时显式说明清理/恢复。
- **可维护**：统一命名、减少重复，需求或缺陷变化时可定位并更新。

## 方法选择

| 场景 | 首选方法 | 最低覆盖提示 |
| --- | --- | --- |
| 单个输入字段 | 等价类 + 边界值 | 有效/无效类；min-1、min、max、max+1、空、超长、特殊字符 |
| 业务流程 | 场景法 | 正常、失败、取消、重试、恢复 |
| 多条件组合 | 判定表/因果图 | 条件组合、互斥、优先级和结果 |
| 多浏览器/设备/配置 | 正交试验 | 先保留主流和高风险组合，再压缩组合数 |
| 异常/鲁棒性 | 错误推测 | 历史缺陷、空值、错别字、乱码、噪声、超时、重复请求 |
| 状态机/工作流 | 状态转换 | 合法/非法跳转、回退、重复提交、终态 |
| Agent | 多样性 + 上下文 + 对抗 + 一致性 | 同意图改写、缺省、插话、长上下文、诱导越权、重复采样 |

## 用例压缩与展开规则

先建立“判据 -> 等价类/状态/条件组合 -> 代表数据”的覆盖骨架，再决定是否展开为独立用例：

- 步骤、前置、Oracle 和清理一致，仅输入不同：保留一条参数化用例和版本化数据表。
- 多条件业务规则：优先用判定表覆盖有效组合，避免为每个排列复制整条步骤。
- 浏览器/设备/配置组合：用风险优先的正交组合；核心路径保留所有批准目标环境。
- 同一失败模式被多个变体触发：保留来源标签和数据行，不复制同义用例。
- 步骤、权限、外部副作用、恢复动作或判定方式不同：拆成独立用例。

每个参数化数据行仍需有稳定 `data_id`、来源、期望、风险和版本，确保失败能定位到具体输入。`representative_cases` 模式只交付覆盖骨架与代表行；`baseline_ready` 才要求完整入库字段。

## Agent 用例补充字段

```markdown
| 字段 | 内容 |
| --- | --- |
| 对话轮次/上下文 | 单轮或第 N 轮；前序事实 |
| 用户输入 | 原始或变体输入 |
| 期望解析 | 实体、数值、单位归一化；不适用则标明 |
| 关键输出 | 必须匹配的字段、范围、候选集合或事实 |
| 强制约束 | Schema、拒绝规则、业务规则、禁止项 |
| 判定方式 | 精确数值 / 字段 / 规则 / Schema / 人工量表 |
| 采样计划 | 引用已批准计划；未定义时交由 `agent-nondeterministic-evaluator` 按其参考文件中的规范默认策略及风险确定 |
| 正式阈值 | 引用已批准项目或适用评测规范；草案允许写 `UNAPPROVED` + 批准责任人/期限，不能空白或虚构 |
| 风险与来源 | 高/中/低；脱敏日志/历史失败/人工构造/对抗集 |
```

计费、计算、权限和安全用例必须使用精确规则或人工复核，不能用平均语义相似度代替。示例阈值不得直接成为准出阈值。

## 跨技能交接包

```yaml
handoff_packet:
  packet_version: 1
  producer: test-scope-case-designer
  delivery_mode: scope_only | representative_cases | baseline_ready
  project_version: null
  snapshot_id: null
  upstream_packet_refs: []
  scope_status: DRAFT | REVIEW_REQUIRED | APPROVED | BLOCKED
  reused_scope: []
  changed_scope: []
  artifact_refs: []
  blocking_gaps: []
  approved_exclusions: []
  next_skill: test-tool-governor | test-process-governor | agent-nondeterministic-evaluator | release-regression-gatekeeper | null
  invalidation_triggers: []
```

`snapshot_id` 绑定需求/代码/配置/Agent 清单、风险依据、阈值配置、用例/数据版本和查询时间。下游若发现绑定项变化，只退回受影响范围，不要求全量重做。

`scope_status=APPROVED` 只能引用产品/研发/测试等适用角色的真实评审证据；本技能不得自行把草案标成已批准。无评审证据时使用 `DRAFT` 或 `REVIEW_REQUIRED`。

## 评审与维护

检查以下事项：

- 每个需求点和高风险影响都有用例或正式排除依据。
- 正向、异常、边界、恢复和安全场景均有明确判据。
- CP0/CP1 用例优先级、冒烟、回归、自动化和安全标签正确；缺陷 P0/P1 不与其混写。
- Agent 用例的采样、阈值、判定和关键字段完整。
- 无重复、过时或只描述实现细节的用例。
- 产品、研发、测试已确认业务规则、技术边界和不可测项。

按“项目 -> 模块 -> 功能 -> 用例”维护单一事实源。把用例、数据、基线和执行记录纳入 Git 或团队平台；线上缺陷必须补充回归用例并保留来源。

测试团队可维护权威用例源；产品/研发按职责评审并使用只读或受控权限。禁止平行复制多个“最新版”，但必须通过 Git/tag/平台版本保留与代码版本对应、不可覆盖的历史。

交付执行时，要求发布前冒烟用例 100% 执行，阻塞问题修复；执行状态使用通过/失败/阻塞，失败关联缺陷、优先级和目标修复版本。实际执行门禁由 `test-process-governor` 和 `release-regression-gatekeeper` 判定。

模板最终化前不得残留 `[占位符]`、无来源数字或虚构审批/责任人。未知字段写 `UNKNOWN` 或 `UNAPPROVED`，并给出责任人、期限和对门禁的影响。
