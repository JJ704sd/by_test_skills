# 发布门禁、验证与关闭

## 发布方式

| 场景 | 默认方式 | 说明 |
| --- | --- | --- |
| 低风险日常迭代 | 全量发布 | 可一次全量；风险上升时先约 10% 验证 |
| 高风险/影响面大/大版本/Agent 核心变更 | 灰度 -> 逐步放量 -> 全量 | 每阶段确认后推进 |
| 线上缺陷严重度 P0/P1 且无法通过配置切换或回滚恢复 | Hotfix，一次性全量 | 优先恢复服务，必须保留回滚并在 24 小时内复盘 |

日常版本使用固定窗口；Hotfix 随时评估；大版本使用规划窗口和灰度期。原规范给出核心业务 09:00-19:00 原则上不发布；物化该 `spec_default` 时必须记录时区、业务日历/节假日和来源版本，缺失时不得直接套用。确需偏离时必须有批准、值守和风险补偿。

## 审批顺序

1. 测试提交测试报告和发布申请。
2. 产品确认业务内容和验收。
3. 测试负责人确认回归与风险。
4. 项目负责人批准发布方式和窗口。
5. 运维在审批后执行部署。

Hotfix 仅允许项目负责人审批记录事后补录；部署前仍需在线授权并记录授权人、时间和范围。

## 发布前置

- 版本包、发布清单、变更说明、影响范围和风险已提交。
- 回归准出、缺陷统计和产品验收已有证据。
- 配置和数据库变更可复查；Agent 的 Prompt、模型参数、工具、知识库和 Schema 已固化。
- 缺陷修复清单和影响范围已同步给运维及业务方。
- 预发布完成最终冒烟；灰度分流/白名单已配置。
- 回滚包/稳定配置、步骤、负责人和恢复验证已确认。
- 测试、产品、项目负责人、运维和值守/发布群已就绪。

禁止无审批、无文档、无验证的发布。记录版本、时间、操作人、阶段、结果和异常处置。

## 异常升级

- `defect_severity=P0`：立即上报项目负责人，目标 5 分钟内响应。
- `defect_severity=P1` 或核心体验受损：10 分钟内上报，立即停止放量并按回滚规则执行。
- 其他异常：在发布群通报时间、影响、处置人和后续动作。

## 发布后 30 分钟内验证

这里是发布授权范围内的只读、低频健康检查、核心哨兵和被动生产遥测，不是生产压测、安全扫描或故障注入。

### Agent

- 基础连通健康检查正常且非空。
- 执行规范默认的 5-10 个版本化核心 Prompt；成功率 = 满足全部批准技术与语义判据的 Prompt 数 / 计划 Prompt 数，规范默认 `>=90%`。
- P95 响应不超过可比基线 1.5 倍；记录查询集合、样本、基线窗口和当前窗口。
- 每个核心工具分别计算成功调用数 / 纳入调用数，规范默认 `>=95%`；不得只报总体平均。
- 输出符合约定 Schema；“错误率无显著上升”必须引用生效阈值记录，未量化时不得用主观判断推进。

核心 Prompt 成功率是版本化哨兵的语义/业务判定，工具调用成功率是按工具统计的调用契约结果，请求错误率是生产技术请求口径；三者分母和用途不同，不能互相换算或用一个指标替代另一个。

### Web/API

- 首页和核心页面可用，无 5xx。
- 登录、下单、支付等核心流程成功。
- 核心 API 返回成功且数据正确。
- 监控无新增缺陷严重度 P0/P1 告警；日志异常必须按生效阈值记录判定，“大量”未量化时不得据此声称通过。
- 数据库变更后数据正确，无死锁或异常慢查询。

这些是规范默认值，`policy_class=spec_default`；项目 SLO 更严格时采用更严格的同口径值。技术失败、语义失败和监控缺失分别记录：监控缺失导致无法判定时为 `BLOCKED`，不能记作成功或零错误。验证完成后继续观察 30 分钟至 2 小时，覆盖错误率、延迟、资源、业务指标、用户反馈和告警。

## 发布关闭

全部满足后才能结束值守并关闭：

- 线上核心验证通过。
- 监控和业务指标在观察期内稳定。
- 无新增缺陷严重度 P0/P1。
- 发布、灰度、异常和验证记录已归档。
- 测试、开发、产品、运维等相关人员已同步结果和遗留项。

## 角色

- 测试：回归、缺陷验证、发布验收、线上验证和风险确认。
- 开发：版本、自测、修复、发布/回滚配合和问题排查。
- 产品：业务验收、发布内容和线上效果确认。
- 运维/部署：环境、部署、灰度、监控、告警和回滚操作。
