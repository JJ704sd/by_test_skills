## 适用原则

NFR 工具选型从指标、负载/故障模型、环境和证据需求出发，不从“流行工具清单”出发。输出必须标记来源层：

- `primary_spec`：《测试工具选型与使用规范》明确的性能、安全、日志/监控、Trace/回放、Agent 评测以及工具稳定性/可维护性。
- `cross_spec`：范围规范的指标与场景需求、流程规范的环境/证据门禁、发布规范的生产遥测/灰度观察，以及 Agent 规范的采样、耗时和工具失败记录。
- `project_approved`：团队标准、许可证、版本、SLO、环境与安全制度中已批准的要求。
- `governance_enhancement`：系统化故障注入、RTO/RPO、无障碍、数据对账、工具校准和运行成本归集等五份规范未完整定义的能力。

不得把 `cross_spec` 或 `governance_enhancement` 冒充工具规范原文。

只有项目已经批准具体产品和版本时才将其写成标准。版本、许可证、维护状态或兼容性可能变化而未核实时，标为待验证；不要宣称“最新”或“最佳”。

## 能力而非品牌

先写能力契约：

- 需要产生什么负载、协议、数据分布、并发/到达率和持续时长？
- 需要控制哪些依赖、故障、延迟、错误、Schema 或区域状态？
- 需要采集哪些 SLI、原始样本、资源、日志、Trace 和业务结果？
- 结果如何关联版本、配置、请求、区域、模型或工具？
- 如何在 CI、定时任务或隔离演练中复现？
- 失败时如何停止、清理数据并恢复环境？
- 工具自身容量、误差、采样、重试和丢数如何校准？

工具不具备判定业务正确性的能力时，必须配合权威 Oracle、契约断言或人工复核；不能用“请求成功”代替质量通过。

## NFR 能力矩阵

| NFR 域 | 必需工具能力 | 关键限制/风险 | 必留证据 |
| --- | --- | --- | --- |
| 性能/容量 | 协议支持、负载模型、分布式发压、百分位、错误分类、资源关联 | 负载器自身饱和、协调时钟、网络瓶颈、重试放大 | 脚本/数据/配置版本、原始样本、负载器与服务资源曲线 |
| 可靠性/长稳 | 长时间运行、失败保留、断点/恢复、泄漏和资源趋势 | 自动重试掩盖原始失败、日志轮转丢证据 | 原始失败、重试前后计数、趋势和运行时间线 |
| 韧性/恢复 | 在隔离环境控制延迟、超时、错误、断连、资源或区域故障 | 故障范围失控、环境污染、回切失败 | 注入计划、审批、时间线、停止/恢复动作、RTO/RPO 测量 |
| 安全/隐私 | 鉴权/授权、输入攻击面、依赖/配置检查、脱敏和审计验证 | 误伤环境、敏感数据留存、误报/漏报 | 规则/版本、扫描范围、人工复核、脱敏报告和清理记录 |
| 兼容/互操作 | 客户端/OS/协议/Schema 矩阵、设备或模拟环境 | 模拟器与真实设备差异、组合爆炸 | 支持矩阵、组合选择依据、结果和失败日志 |
| 可观测/可运维 | 指标、日志、Trace、关联 ID、告警路由和查询版本化 | 采样丢失、时钟偏差、高基数、PII/Secret 泄露 | 仪表盘/查询、告警送达、Trace 样本、脱敏抽检 |
| 数据完整性 | 数据准备、对账、校验和、事件序列、回放和清理 | 非幂等写入、测试数据越界、恢复污染 | 数据版本、前后快照、对账、清理证明 |
| 易用/无障碍 | 任务记录、批准标准的自动/人工检查和辅助技术矩阵 | 自动检查不能覆盖全部体验问题 | 工具报告、人工复核、平台/辅助技术版本 |
| Agent 运行 NFR | 批量/并发、Trace、模型/工具拆分耗时、Token、回放、故障 stub | 提供方限流、缓存、非确定性、敏感 Prompt/输出 | Agent 清单、逐次运行、技术失败、语义结果和用量 |
| 成本效率 | 按版本/场景/成功结果归集调用、Token、资源和存储用量 | 只降成本却损害质量、账单延迟、共享资源分摊 | 用量来源、分摊公式、质量并行指标、基线 |

一个工具可覆盖多个域，但选型记录必须逐能力验收，不能因品牌入选而默认全部能力合格。

## 环境与安全边界

以下禁令不可由审批解除：

- 不在生产执行压测、容量摸底、渗透/安全扫描、破坏性故障注入、删除或修改操作。
- 不让性能、安全、自动化或故障注入脚本默认或回退指向生产。
- 不在仓库、脚本、日志、Trace、报告和测试集中明文保存 Secret 或未脱敏隐私数据。

生产只允许按项目制度进行已批准的只读监控、日志/Trace 分析和非破坏性线上质量采样；它们不能替代隔离环境中的 NFR 测试。

隔离环境执行高负载、安全或故障注入时仍需：明确目标资源、最小权限、审批窗口、值守、停止条件、恢复步骤、数据清理和审计日志。环境名不等于安全隔离，必须确认网络、账号、数据和共享依赖不会触达生产。

## 可信度与可复现性

### 负载与采集校准

- 在低负载下校验请求量、响应、时钟和端到端/服务端计时差异。
- 监控负载生成器、网络和采集端自身资源，识别客户端瓶颈。
- 保存原始错误；分别报告首次尝试、重试和最终结果。
- 记录预热、缓存、连接复用、限流、采样和数据聚合配置。
- 结果异常时先确认工具与环境可信度，再归因被测系统。

### 版本化资产

至少版本化：脚本、非敏感配置、数据/Schema、负载模型、故障清单、断言/Oracle、仪表盘查询、报告模板和环境清单。报告记录提交或制品版本，不只记录文件名。

### 可诊断性

失败证据应能从报告追踪到请求/样本、工具日志、被测服务日志/Trace、版本和配置。仅有聚合图、无法定位个体失败的方案只能限定采用。

### 数据生命周期

定义数据生成、脱敏、授权、传输、存储、访问、保留、导出和清理。工具试用结束后清理临时账号、测试数据和凭据，并保留不含敏感内容的审计记录。

## 试用与验收

新 NFR 工具在隔离、非核心范围试用，并验证：

1. 能否准确产生预期负载/故障或检查动作。
2. 指标与独立计数/服务端记录是否在批准误差内一致。
3. 原始失败、重试、超时和无效样本是否可区分。
4. 报告是否可追溯到版本、配置、数据和请求。
5. CI/定时运行是否稳定，失败是否可诊断。
6. 权限、Secret、隐私、数据清理和环境隔离是否合规。
7. 团队是否能维护；许可证、基础设施、培训、迁移和退出成本是否可接受。

验收目标未批准时可以完成技术试用，但决策状态应为限定采用或待评审，不能声称正式标准化。
