# 测试工具选型与治理

## 职责边界

负责决定“是否需要工具、选哪个、如何安全使用和长期维护”。先确认测试目标，再做选型；不要让工具名称替代覆盖范围、用例判据或质量结论。

本技能验证工具能否测量项目已批准的阈值，不拥有产品 NFR 或 Agent 质量阈值的批准权。

- 范围和用例交给 `test-scope-case-designer`。
- 测试流程门禁交给 `test-process-governor`。
- Agent 指标和准出交给 `agent-nondeterministic-evaluator`。
- 发布与灰度门禁交给 `release-regression-gatekeeper`。

除非用户同时要求实施，否则只输出决策、配置边界和落地计划，不安装依赖、不访问生产、不执行压测或安全扫描。

## 开始前

收集：

- 被测对象、测试类型、风险、频率、并发/样本规模和验收指标。
- NFR/SLI/SLO 配置、负载/故障模型、统计窗口、原始证据和停止/恢复要求。
- 团队现有标准工具、许可证、人员技能、CI/CD 和报告平台。
- dev/test/pre/prod 环境、账号权限、数据敏感性和审批要求。
- 现有脚本/用例/数据、迁移量、维护周期、预算和退出成本。
- Agent 项目的模型、Prompt、Trace、回放、批量采样、基线和语义评估需求。

缺少版本、维护状态或兼容性证据时标为待验证；不要把“常用”写成“已批准”或“最新”。

## 高效执行协议

按请求选择最小决策深度：

- `reuse_check`：判断团队现有标准工具能否满足必需能力；满足时直接复用并列出配置/证据缺口。
- `selection_record`：现有方案不满足时，比较最多 2-3 个有现实落地条件的候选并形成正式决策。
- `implementation_plan`：仅在用户要求落地时补充试用、迁移、CI、培训、维护和退出计划；不等同于已获执行授权。

“最多 2-3 个候选”是减少无效比较的治理启发式，不是来源规范中的绝对数量门禁；当采购、合规或明确的多平台覆盖要求需要更宽比较时，可以扩展，但必须说明原因并先通过硬约束筛选。

先做安全、环境、许可证/可用性和必需能力否决检查，再比较偏好项。一个已批准工具若满足全部硬要求且总拥有成本无新增异常，停止扩展候选，不为“选择感”重复评估同类产品。复用未变化的团队标准、能力验收和环境证据；版本、许可证、维护状态、目标协议/规模、环境或安全制度变化时，只重验受影响项。

只追问会改变安全授权、硬能力或采购/迁移结论的信息；其余未知项标为 `UNKNOWN`，以限定采用或 `REVIEW_REQUIRED` 继续产出。工具事实具有时效性，正式决策必须记录核验日期和来源，过期后不得沿用“最新/受支持”结论。

## 工作流

1. **定义验收目标**：选择决策深度，说明要验证的行为、硬能力、指标、规模、执行频率、证据格式和 CI/CD 需求。
2. **检查团队标准**：优先复用已批准工具和资产；满足硬要求时直接进入配置/治理检查并停止扩展候选，新增同类工具必须说明现有方案为何不能满足。
3. **应用安全否决项**：先检查环境、权限、凭据、生产影响和敏感数据。命中否决项时停止选型/执行并给出整改条件。
4. **形成短名单**：仅在复用检查未通过时读取 [tool-catalog.md](references/tool-catalog.md)，按场景保留最多 2-3 个首选/备选及适用条件和限制；NFR 场景同时读取 [nfr-tooling.md](references/nfr-tooling.md) 做能力、隔离、校准和证据映射。
5. **比较证据**：从统一性、稳定性、可维护性、自动化/CI 能力、场景适配性评估；另列许可、基础设施、迁移、培训和长期维护成本。
6. **设计试用**：按 [governance.md](references/governance.md) 的周期在非核心或内部环境试用，记录成功率、耗时、失败可诊断性、维护量、权限和数据风险。
7. **给出决策**：选择采用、限定采用、不采用或 `REVIEW_REQUIRED`，并单列执行授权；列明版本、配置基线、适用范围、禁止项、迁移和退出方案。
8. **纳入治理**：把脚本、配置、测试集、核心集合和报告模板纳入版本管理及 CI；安排版本复查、Review、培训和废弃流程。

## 安全否决项

命中任一项时，不得推荐直接执行：

- 原工具规范绝对禁止对生产执行压测、渗透、删除或修改测试操作，审批不能解除。
- 治理增强同样禁止对生产执行容量摸底、自动安全扫描或破坏性故障注入，也不能用审批解除。
- 把主动接口调试、通用测试自动化、性能或安全扫描脚本指向生产；这些活动仅允许在显式隔离的 dev/test/pre 环境执行。发布流程批准的版本化只读健康检查按下文例外治理。
- 脚本默认指向生产，或环境变量缺失时回退到生产。
- 共享账号、超额权限，或在脚本/仓库/日志中明文保存密码、Token、密钥和隐私数据。
- 直接覆盖生产 Prompt，或未固化模型、参数、工具、知识库和评测版本。
- 长期资产没有断言、日志、结果统计、版本管理或 CI 可复现路径。
- 用 LLM 评审作为计费、权限、安全或核心业务的唯一证据。

经发布授权的生产部署/回滚属于发布系统操作，不属于上述“测试工具修改”禁令；批准的被动遥测、只读低频健康检查和非破坏性线上质量采样也可执行，但不得扩展为主动压测、扫描或故障注入。

允许的恢复条件包括：改用隔离测试环境、最小权限账号、Secret 管理、只读模式、测试环境审批窗口、脱敏数据、停止条件和可审计日志。不要把“获得审批”当成生产压测或渗透的恢复条件。

## 输出契约

先给明确结论，再按决策深度给材料：

- `reuse_check`：只给现有工具的硬能力/安全结论、配置或证据缺口、使用限制和复核条件；不要求候选市场比较、试用或迁移计划。
- `selection_record`：补充短名单、统一口径比较、总拥有成本、首选/备选和正式决策；只给必要的验证计划。
- `implementation_plan`：才补齐试用、迁移、CI、培训、维护、升级和退出计划。

适用字段至少包含：

1. `selection_decision`：采用 / 限定采用 / 不采用 / REVIEW_REQUIRED；`execution_authorization`：ALLOWED / BLOCKED / NOT_REQUESTED，以及首选和备选。
2. 场景、验收目标、假设和未决证据。
3. 候选比较、选择理由、限制和总拥有成本。
4. 版本、环境、权限、数据、Secret、CI/CD 和报告要求。
5. 试用、迁移、培训、维护、升级和退出计划。
6. 审批/责任人及重新评估条件。

同时给出 `decision_depth`、`snapshot_id`、`reused_evidence`、`changed_constraints`、`facts_verified_at` 和 `invalidation_triggers`，并使用治理参考中的交接包。`reuse_check` 已得出明确结论时不要输出冗长市场对比。

需要正式记录或审计清单时读取 [governance.md](references/governance.md)。若用户要求具体脚本或配置，在落地前再次应用本技能的安全否决项。
