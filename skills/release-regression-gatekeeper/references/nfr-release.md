## 适用边界

本文件把 NFR 组织成发布证据链，输出必须标记来源层：

- `primary_spec`：《版本发布与回归测试策略》明确的高可用链路、性能/错误率/资源观察、数据异常硬回滚、稳定版本/配置恢复、Agent 延迟/工具成功、灰度与回滚。
- `cross_spec`：范围规范的性能/安全/兼容/数据场景、流程规范的测试准出、工具规范的监控/Trace，以及 Agent 规范的请求成功、在线质量和漂移信号。
- `project_approved`：项目批准的 SLO、错误预算、容量、恢复、安全、数据或成本门禁。
- `governance_enhancement`：RTO/RPO、错误预算燃烧、多窗口告警、不可逆迁移恢复、完整韧性/可观测性和运行成本等五份规范未完整定义的方法。

不得把 `cross_spec` 或 `governance_enhancement` 冒充发布规范原文；治理增强只有在项目批准后才构成硬门禁。

本文件不创造项目阈值。数字只能来自可追溯的项目 SLO/发布标准或本技能其他参考文件中的规范默认值；冲突时按 SKILL.md 的规则处理并披露来源。

## 发布前证据包

每个适用 NFR 至少应有：

- 来源、对象、SLI 公式、SLO/目标、窗口、门禁和批准状态。
- 被测版本、环境/拓扑差异、工作负载、数据、工具/脚本和原始证据。
- 当前值、基线、阈值、趋势、样本量、错误分类和结论。
- 高风险失败、缺陷、复测、遗留风险、补偿、责任人和期限。
- 生产仪表盘、查询/告警、拆分维度、值守和异常升级路径。
- 灰度哨兵、阶段推进、停止/回滚和恢复后验证条件。

按风险检查以下域：

| NFR 域 | 发布前关键证据 | 生产门禁准备 |
| --- | --- | --- |
| 性能/容量 | 目标负载、峰值/长稳、百分位、错误率、资源余量和环境差异 | 延迟、吞吐、错误、资源/队列及容量告警 |
| 可用性/可靠性 | SLI 口径、依赖失败、长稳和基线 | 窗口、错误预算、依赖/区域拆分和告警 |
| 韧性/恢复 | 隔离环境故障、降级、切换/回切、回滚演练、RTO/RPO | 停止条件、稳定版本/配置、负责人和验证清单 |
| 安全/隐私 | 高风险缺陷、权限、拒绝、数据/日志脱敏和审计 | 安全事件硬回滚、审计/告警和值守 |
| 兼容/数据 | 支持矩阵、Schema/前后向兼容、迁移/回放/对账 | 客户端/版本拆分、数据校验和回滚兼容 |
| 可观测性 | 指标、日志、Trace、关联 ID、告警演练 | 仪表盘/查询就绪、告警送达和 Runbook |
| Agent 运行 NFR | 离线门禁、延迟、每工具成功、故障降级、质量保持、Token/成本 | 解析/任务成功、工具/Schema、质量/安全、延迟和漂移信号 |
| 成本效率（治理增强） | 单位成功成本、Token/调用/资源基线和质量并行结果 | 经批准的成本警戒信号；不能用降质换成本达标 |

数据库或 Schema 变更不能假设“代码回滚即数据恢复”。不可逆迁移发布前必须有迁移前快照/备份、对账、前后向兼容或经批准的向前修复方案，并演练恢复验证；证据缺失时不得把回滚标为就绪。

强制证据缺失时不得推定通过。信息无法核实时为 `BLOCKED`；已确认未达硬门禁时为 `NO_GO`。

## SLO、错误预算与发布阈值

必须区分：

- **长期 SLO**：在批准窗口内衡量服务目标。
- **错误预算**：由批准的 SLO 和实际 SLI 口径计算的容许失败空间。
- **灰度阶段门禁**：一次发布在短窗口内的推进或停止条件。
- **硬回滚条件**：确认后立即触发停止与恢复动作的安全/质量/技术事件。

长期 SLO 达标不能抵消本次版本的硬回滚事件；短期灰度正常也不能证明长期 SLO 已完成。只有项目发布标准明确规定错误预算燃烧阈值和动作时，才用它直接触发停止/回滚；否则把它作为 `WATCH` 或升级信号并要求责任人判定。

项目 SLO、发布门禁和规范默认值冲突时，采用适用且可追溯的更严格规则。若适用范围或口径不同，不能只比较数字大小；先列出冲突并取得责任人裁决。

## 灰度阶段判定

每一阶段开始前冻结版本、配置、流量/白名单、观察时长、指标、基线、阈值和操作人。推进前检查：

1. 核心哨兵、业务正确性和安全拒绝无失败。
2. 错误率、延迟、吞吐、资源/队列和依赖信号在批准范围。
3. Agent 按模型、工具、Schema、区域拆分的技术与质量信号无硬失败。
4. 数据完整性、兼容性、隐私和审计无异常。
5. 告警、日志、Trace 和关联 ID 可用，样本量足以支持该阶段判定。
6. 没有新增缺陷严重度 P0/P1，上一阶段异常已闭环并记录。
7. 测试与运维按规范完成阶段确认。

指标缺失、采集失真、版本/配置漂移或阶段未确认时，不得继续放量；根据可核实程度给 `BLOCKED` 或保持当前阶段。

报告总体值的同时，按版本、区域、客户端、模型和每个核心工具做风险相关拆分。总体平均值不能掩盖一个核心分片或工具失效。

## 停止与回滚

按 [rollout-rollback.md](rollout-rollback.md) 的硬条件和阶段阈值执行。NFR 还需把下列已批准事件映射到动作：

- 核心可用性、错误率、延迟、数据或恢复门禁被突破。
- 错误预算按项目发布标准达到硬停止/回滚燃烧条件。
- 模型/工具达到生效阈值记录中的硬失败条件，且无法按批准行为安全降级；“大面积”未量化时不能开始该阶段。
- 关键监控失明，使继续放量无法可靠判断风险。

任何确认的误计费、越权、安全拒绝失效、敏感数据泄露、核心数据错误或缺陷严重度 P0/P1，均不能被性能或可用性总体值抵消。

触发后：

1. 立即停止当前发布/放量并保全证据。
2. 按已批准的稳定版本或配置回滚，不临时发明恢复方案。
3. 验证服务、核心链路、数据/Schema、权限、安全拒绝、关键 NFR 和告警恢复。
4. 在批准观察窗口内确认稳定，记录实际恢复时间和数据恢复点。
5. 回滚不安全或失败时保持停止，升级事故指挥，不得继续放量。

生产禁止以“验证 NFR”为由主动执行压测、安全扫描或破坏性故障注入。发布过程只观察真实流量、批准的非破坏性哨兵和生产遥测。

## 发布关闭与长期观察

关闭发布至少要求：

- 发布后核心验证与全部阶段门禁通过。
- 适用 NFR 在规定观察期稳定，无新增缺陷严重度 P0/P1 或未处置异常。
- 灰度、告警、异常、操作和验证记录完整并已同步。
- 遗留风险、长期 SLO/错误预算观察和责任人已交接。

一次发布关闭不代表长期可用性或可靠性目标永久满足。长期窗口尚未结束时，报告“当前发布观察通过，SLO 持续观察中”，不要伪造完整周期结论。
