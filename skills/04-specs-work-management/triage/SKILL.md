# Triage

If tracker or label conventions are missing, run `$configure-engineering-skills` first. Include external PRs only when `docs/agents/issue-tracker.md` marks them as a request surface.

Every issue, PR, or comment posted during triage must begin:

```text
> *This was generated by AI during triage.*
```

## Roles

Assign exactly one category role (`bug` or `enhancement`) and one state role:

- `needs-triage`: maintainer evaluation is pending
- `needs-info`: waiting for the reporter
- `ready-for-agent`: fully specified for AFK work
- `ready-for-human`: implementation requires human judgment or access
- `wontfix`: closed without implementation

Resolve canonical roles through `docs/agents/triage-labels.md`. If state labels conflict, stop and ask the maintainer. Treat unusual transitions as recommendations until confirmed.

## Show work needing attention

Query the configured tracker and show, oldest first:

1. unlabeled inbound items
2. items in `needs-triage`
3. `needs-info` items with reporter activity after the latest triage note

When external PRs are enabled, include only non-maintainer PRs in discovery and label every result `[issue]` or `[PR]`. An explicitly named PR is always eligible regardless of author.

## Triage one item

1. Read the full body, comments, labels, author, dates, prior triage notes, and PR diff when applicable. Explore relevant code and domain docs. Search by domain concept for an existing implementation. Read [references/out-of-scope.md](references/out-of-scope.md) for the rejection workflow, then inspect the repository's `.out-of-scope/` records for prior rejections.
2. Recommend category and state with evidence, including where redundancy was checked. Wait for maintainer direction.
3. Verify the claim before interviewing: reproduce a bug, or check out and test a PR's stated behavior. Report confirmed, failed, or insufficient evidence.
4. If decisions remain, use `$grilling` in documented mode so `$domain-modeling` records only resolved vocabulary and ADRs.
5. Apply the confirmed outcome:
   - `ready-for-agent`: post a brief using [references/agent-brief.md](references/agent-brief.md).
   - `ready-for-human`: use the same structure and state why it cannot be delegated.
   - `needs-info`: post [assets/needs-info-template.md](assets/needs-info-template.md).
   - `wontfix`: distinguish already implemented, rejected bug, and rejected enhancement; only rejected enhancements update `.out-of-scope/`.
   - `needs-triage`: apply the role, with an optional progress comment.

## Overrides and resumption

For a direct maintainer state override, summarize the intended label, comment, and close actions, then apply the confirmed change without grilling. When moving directly to `ready-for-agent`, ask whether an agent brief is wanted.

On resumption, parse prior notes and reporter replies, present the updated state, and never re-ask resolved questions.
