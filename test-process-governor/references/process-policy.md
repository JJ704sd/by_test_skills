## 端到端阶段

| 阶段 | 输入 | 必做动作 | 输出/证据 |
| --- | --- | --- | --- |
| 需求分析 | 需求文档、原型、业务规则、变更说明 | 需求评审；确认业务逻辑、范围、验收标准、依赖、风险和测试难点 | 评审纪要、待确认项、初步测试范围 |
| 测试设计 | 已评审需求、初步范围 | 设计正常、异常、边界、业务和兼容场景；先组内评审，再做产品/研发/测试三方评审 | 已评审用例、范围清单、数据与环境准备清单 |
| 开发实现 | 已评审需求和用例 | 开发编码；完成单元、集成和自测；提交可测版本及自测报告 | 提测版本、变更/影响说明、开发自测报告 |
| 版本测试 | 提测版本、自测报告、环境与数据 | 提测准入、冒烟、系统测试、缺陷管理、修复点及影响面回归、产品验收、测试报告 | 执行记录、缺陷与回归证据、验收记录、测试报告 |
| 上线与复盘 | 已评审测试报告、产品验收结果、发布材料 | 上线风险评估、发布准备、生产发布、线上核心验证、测试复盘 | 上线确认单、线上验证报告、风险结论、复盘纪要与回流项 |

保持主链路：需求评审 -> 用例设计 -> 组内评审 -> 三方评审 -> 开发自测 -> 提测 -> 准入 -> 冒烟 -> 系统测试 -> 缺陷 -> 回归 -> 产品验收 -> 测试报告 -> 上线评审 -> 发布 -> 线上验证 -> 复盘。

保持失败回流：三方评审不通过时返回用例设计；提测准入、冒烟、产品验收或上线风险评估不通过时返回开发实现/修复，并在重新提交后重跑受影响门禁。不要让失败节点沿主链路继续流转。

## 项目差异化

| 类型 | 允许的流程调整 | 不可省略项 |
| --- | --- | --- |
| 常规迭代 | 无；执行完整标准流程 | 全阶段记录、评审、测试和发布验证 |
| 紧急修复/热更 | 三方用例评审可压缩为组内快速确认；仅验证修复点和核心影响面；快速验收与发布 | 测试负责人把控、修复点验证、核心冒烟、影响说明、回滚预案和上线验证；“24 小时内复盘与用例回流”为发布规范的跨规范补充 |
| 大版本/重构 | 在标准流程上加固 | 完整用例与三方评审、全量回归、核心场景加固、交叉测试、多环境/预发布验证；“按风险执行兼容、性能和稳定性测试”为范围/发布规范的跨规范补充 |

## 测试原则

- 尽早参与需求阶段，先关闭歧义和不可测点。
- 围绕业务、功能、异常、边界和兼容性覆盖关键场景。
- 对用例、执行、缺陷、回归、报告和发布结论保留可追溯证据。
- 以业务风险和用户影响决定优先级，不以用例数量代替覆盖质量。
- 对无法自动判断或高风险的场景保留人工验证。

## 提测准入

全部满足后才进入正式测试：

- 需求已评审，重大歧义已关闭或登记为明确风险。
- 开发已完成自测，无阻塞性问题，并提交自测报告。
- 测试环境、数据、账号、权限和依赖服务已就绪。
- 版本可安装/可部署，服务正常，关键接口可调用。
- 测试范围、用例、优先级和执行计划已确认。

## 测试暂停条件

命中任一项即暂停并升级：

1. 冒烟失败率超过 30%，或核心流程存在 P0 阻断。
2. 测试环境不稳定、服务异常，导致结果不可信或无法继续执行。
3. 出现无规避方案的 P0 缺陷。
4. 开发频繁变更版本且未通知测试，导致测试不可控。

暂停记录必须包含触发证据、影响范围、当前版本、责任人、恢复条件和恢复后的重跑范围。

## 测试准出与结束

准出至少满足：

- 计划内用例执行率 100%；阻塞项已有正式结论。
- P0/P1 缺陷 100% 修复并回归通过。
- 修复点、缺陷影响面和关联功能已回归，无新增阻塞。
- 产品完成最终验收。
- 测试报告已评审并同步，遗留风险可接受且有责任人和计划。
- 上线风险评估完成，无不可接受风险。

只有在准出达成、报告评审同步、上线风险评估完成、产品最终验收通过、全部缺陷按规则关闭或纳入跟踪后，才可标记测试结束。

正式测试从提测准入通过开始，到产品验收通过结束。回归可随修复动态安排；常规版本在上线前必须完成发布策略按变更与风险选定的回归层级，只有大版本/重构或高风险策略明确要求时才是全量回归；紧急修复按已批准的最小影响范围执行。

在计划上线截止时间前 4 小时停止该计划版本的**所有测试活动**，为风险评估、发布准备和线上验证预留时间；不能把它改写成仅“停止新增”。另行授权的 Hotfix 修复验证、回滚恢复冒烟和发布后只读验证属于独立的紧急/发布流程，不是继续该计划版本的常规测试；必须单独记录授权、版本、范围和证据。若组织对计划版本另有经批准的收尾规则，把它标为项目偏离并记录批准人、原因、剩余风险和补偿措施。

## 缺陷分级

| 等级 | 定义 | 示例 | 处理规则 |
| --- | --- | --- | --- |
| P0 Blocker | 核心流程完全不可用或无法继续测试；严重安全/数据风险为跨规范治理补充 | Agent 无法启动、核心 API 全部失败；数据丢失、安全绕过为跨规范示例 | 立即升级；本轮修复并回归；不得上线 |
| P1 Critical | 主要功能异常、无合理规避方案，影响核心用户或业务决策 | 核心字段频繁错误、关键上下文丢失、主要接口异常 | 本轮修复并回归；不得遗留上线 |
| P2 Major | 非核心功能异常，有规避方案，不阻塞主流程 | 边缘流程、提示或部分兼容性问题 | 可纳入后续版本，但必须跟踪闭环 |
| P3 Minor | 不影响使用的轻微问题 | 拼写、对齐、非关键文案 | 进入优化队列，定期处理 |
| P4 Trivial | 建议类体验或文案优化，不构成缺陷 | 交互体验、文案润色 | 按产品优先级处理 |

原规范明确了 P0/P1、P2、P3 的处理硬规则；上表 P4 处理是为保持缺陷生命周期完整而补充的治理规则，不得用它放宽 P0-P3 门禁。

## 缺陷生命周期

1. **提交**：写清标题、版本/环境、前置条件、步骤、实际/期望结果、严重度和截图/日志/Trace。
2. **确认**：开发接受或拒绝；拒绝必须给出可核对理由，如设计如此、重复或无法复现。
3. **修复**：记录修复版本、影响范围和必要的开发验证。
4. **待验证**：测试准备修复点与影响面回归。
5. **验证**：通过则关闭；失败则重新打开，并保留新证据。
6. **挂起**：仅对环境/数据等暂不可解问题使用；需产品与测试确认，记录原因、风险、责任人和目标版本。

## 角色职责

| 阶段 | 测试 | 开发 | 产品 | 运维/部署 |
| --- | --- | --- | --- | --- |
| 需求/设计 | 识别风险，设计并组织用例评审 | 评估技术可行性和边界 | 解释需求并确认验收标准 | 按需评估环境和发布约束 |
| 开发/提测 | 跟踪进度，准备环境数据，检查提测材料 | 编码、自测、提交版本和自测报告 | 确认业务范围 | 准备测试/预发布环境 |
| 版本测试 | 准入、冒烟、系统测试、缺陷、回归和报告 | 修复并配合验证 | 参与验收 | 支持环境、日志和依赖排障 |
| 上线/复盘 | 风险确认、线上验证、复盘与回流 | 配合发布、监控和问题排查 | 线上业务验收 | 部署、监控、灰度和回滚 |
