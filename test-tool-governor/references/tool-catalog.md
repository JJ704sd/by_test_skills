# 测试工具目录与使用规则

本文件整理自《测试工具选型与使用规范》（2026-05-08）。工具名称表示内部默认标准，不表示无条件采用；先验证团队现状、许可证、维护状态和项目约束。

## 标准工具矩阵

| 场景 | 首选 | 备选/补充 | 限制 |
| --- | --- | --- | --- |
| 用例与缺陷管理 | 禅道（中小项目）；TAPD（缺陷/用例协同场景） | TestLink（大型或专门用例库） | 按团队既有标准选一套权威源；Excel 仅用于临时项目，不作长期正式用例库 |
| 接口调试与联调 | Apifox | Postman | Postman 仅临时调试；关键集合迁入团队标准平台；Swagger 只用于查阅接口文档 |
| 接口自动化 | Pytest + Requests + Allure | Robot Framework | 临时手写脚本不得长期漂移；正式资产必须进入 Git 和 CI，Allure 统一报告格式 |
| Web UI 自动化 | Playwright | Selenium | 新项目不优先 Selenium；仅覆盖稳定高价值链路 |
| 性能 | JMeter | Locust | 只能在隔离非生产环境执行；审批不能允许压生产；复杂 Python 压力模型可选 Locust |
| 安全 | OWASP ZAP | Burp Suite | 只能对明确授权的隔离非生产目标执行；审批不能允许扫描或渗透生产 |
| 日志/监控 | Kibana、Grafana、Sentry、公司统一平台 | 项目现有平台 | 不导出敏感日志；优先用 Trace ID 定位 |
| Prompt 调试/管理 | Playground、Langfuse | 自研配置平台 | Prompt 必须版本化，禁止直接覆盖生产 |
| Trace/回放 | LangSmith、自研日志平台 | 项目统一平台 | 记录模型、参数、Prompt、工具调用和上下文版本 |
| LLM/Agent 评测 | Promptfoo、DeepEval、自研评测脚本 | 业务规则脚本、人工复核 | 必须有测试集和基线；LLM 评审不是核心结论的唯一证据 |

## 用例与接口工具

- 按模块组织用例，统一命名，明确 `case_priority=CP0/CP1`、smoke 和 regression 标签；缺陷严重度另用 P0/P1。
- Apifox 显式区分 dev/test/pre/prod；域名、Token 和业务参数使用安全的环境配置，不硬编码。
- 核心接口断言至少覆盖 HTTP 状态码、关键响应字段和业务错误码；补充鉴权、边界、幂等、超时和依赖失败。
- 将核心接口集合和可复现环境配置导出并纳入版本管理；不要保存 Secret。

## Pytest 与接口自动化

- 测试文件使用 `test_*.py`，测试函数使用 `test_*`。
- 用 fixture 管理登录、环境、数据和公共前置；用参数化覆盖数据变体。
- 支持 Jenkins/GitLab CI、失败日志、报告和结果统计，至少记录通过率、失败原因和执行时间。
- 使用重试时记录次数和原始失败；不要把偶发重试掩盖成稳定通过。

## Playwright 与 UI 自动化

- 只长期自动化稳定的登录、冒烟、主链路和高价值场景。
- 优先稳定定位器，避免脆弱 XPath；录制脚本必须整理并添加业务断言后才能入库。
- 高频变化页面、强依赖样式页面、复杂拖拽和一次性场景先评估维护成本。

## 性能工具

- 执行前定义并发、目标 TPS、持续时长、Ramp-up、压力模型、数据模型和停止条件。
- 同时采集 P90/P95/P99、TPS、错误率、CPU、内存、数据库、缓存和依赖服务指标。
- 集中管理域名、并发、时长和数据，禁止把参数散落在脚本中。
- 优先使用接近生产配置的隔离环境。原规范禁止对生产执行压测；即使有值守或审批，也应迁移到隔离环境。

## 安全与日志工具

- 安全检查至少考虑认证、授权/越权、SQL 注入、XSS、Token 有效性和日志脱敏；按项目补充命令注入、敏感数据和 Agent 工具权限。
- 日志平台应支持 Trace ID、错误检索、时间过滤和请求链路定位。
- 不在日志中输出密码、Token、密钥和隐私；不把敏感日志导出到个人设备或仓库。

## Agent 工具

- 固化模型版本、temperature、top_p、system prompt、工具定义、知识库和评测脚本版本。
- Prompt 修改必须保留历史；严格检查测试与生产模型版本/参数差异，不能用不可比环境替代发布结论。
- 使用结构化测试集，至少保存输入、关键期望、约束、标签、风险和数据来源。
- 非确定性场景引用 `agent-nondeterministic-evaluator` 的批准采样策略或规范默认策略，并与同一测试集上的可比基线比较。
- 分开记录技术失败和语义失败；保留请求 ID、Trace、耗时和原始输出。
- 对复杂语义可用 LLM 辅助评审，但计费、计算、权限、安全和强 Schema 使用规则校验或人工复核。

## Agent 判定能力验收

工具规范中的 Agent 表包含 100%、98%、90%、85% 等质量数字，但这些数字不归工具技能批准，也不能因“工具支持”而自动成为产品或发布门禁。产品阈值由项目批准的 `threshold_profile` 和 `agent-nondeterministic-evaluator` 解释。

这里只验证候选工具能否准确表达当前阈值配置所需能力：

| 判定类型 | 工具能力要求 |
| --- | --- |
| 核心计费/计算 | 精确数值或明确的绝对/相对容差；保存输入、公式和逐次结果 |
| 实体与单位 | 字段级比较、归一化规则、分子/分母和失败样本 |
| 推荐/复杂语义 | 批准候选/量表、人工复核和评审一致性记录 |
| 鲁棒/安全拒绝 | 固定数据集、每次有效运行、任何高风险漏过可定位 |
| 输出格式 | Schema/规则版本、字段差异和原始输出 |

如果工具精度、数据类型、聚合方式或原始证据无法满足 `threshold_profile`，则限定采用或不采用；不得通过修改产品阈值迁就工具。
