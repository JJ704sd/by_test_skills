# 测试范围与用例设计

## 职责边界

负责回答“测什么、测到多深、为什么、如何判定”。输出范围、排除项、风险依据、可执行用例和追踪关系；不要虚构已经执行的结果。

产品/业务/架构及适用的安全、运维角色负责批准 NFR/SLO 和风险接受标准；本技能负责记录来源、暴露缺口并将其转成可测判据，不自行批准或发明阈值。

- 测试阶段与准入准出交给 `test-process-governor`。
- 工具和环境方案交给 `test-tool-governor`。
- Agent 的批量采样、指标计算和基线结论交给 `agent-nondeterministic-evaluator`。
- 回归层级、发布、灰度和回滚交给 `release-regression-gatekeeper`。

## 开始前

尽量收集：

- 需求、原型、验收标准、接口契约和业务规则。
- 代码/配置/Prompt/模型/工具/知识库差异及发布说明。
- 模块、接口、数据流、依赖服务、权限和兼容性矩阵。
- 历史缺陷、线上投诉、失败日志、性能基线和安全风险。
- 已批准的 NFR、SLA/SLI/SLO、容量/恢复目标、支持矩阵、合规要求和生产基线。
- 目标环境、数据、时间、人员和允许的排除范围。
- 预计用例数、执行轮次、自动化目标和可用人力，用于资源估算。

信息不足时仍可输出“初版范围”，但必须显式列出假设、未知项、待确认人和重新评估条件；不要把初版称为完整覆盖。

## 工作流

1. **建立变更清单**：按新增、修改、删除整理功能、接口、数据、配置和外部依赖；对 Agent 额外列出 Prompt、模型、参数、工具、知识库、上下文和 Schema。
2. **绘制影响链**：从变更点追踪上游、下游、共享组件、数据一致性、权限、资金/计费、高频路径和历史脆弱点。
3. **评定风险**：对每个对象给出高/中/低等级、发生可能性、影响和依据。读取 [scope-policy.md](references/scope-policy.md) 选择默认深度。
4. **选择测试类型**：逐项说明功能、接口、NFR 和 Agent 非确定性是必测、按需还是排除；排除必须有原因、责任人和重新纳入条件。涉及性能、容量、可用性、可靠性、恢复、安全、兼容、可观测、数据完整性、体验/无障碍或成本时读取 [nfr-design.md](references/nfr-design.md)。
5. **建立覆盖矩阵**：形成“需求/变更/NFR -> 风险 -> 指标/判据 -> 负载或故障模型 -> 场景/用例 -> 用例优先级 -> 自动化候选 -> 证据”的追踪关系。
6. **估算资源**：用用例数、执行轮次、自动化覆盖目标、环境组合和人工复核量估算工作量与人力；披露估算假设。
7. **设计用例**：按场景选择等价类、边界值、场景法、判定表/因果图、正交、错误推测、状态转换或 Agent 专项方法。读取 [case-design.md](references/case-design.md) 保持字段和判据完整。
8. **评审与基线化**：检查完整性、准确性、可执行性、独立性、可维护性和优先级；按编写、组内交叉评审、三方评审、结论入库推进，将用例和数据纳入统一版本管理。

## 不可放宽的设计规则

- 每条预期结果必须可观察、可判定；禁止只写“正常”“符合预期”。
- 每个核心需求至少覆盖正常、异常、边界和失败后的恢复/重试路径。
- 资金、计费、权限、敏感数据、安全拒绝和数据一致性必须按高风险处理。
- 排除项必须写明原因、风险所有者和重新评估条件，不能静默漏测。
- Agent 用例必须包含关键字段/约束、判定方式、采样计划和正式阈值引用；尚未批准时显式写 `UNAPPROVED` 及责任人/期限。一次输出不能代表非确定性质量。
- NFR 判据必须写明来源、公式、单位、范围、统计窗口、环境/负载或故障模型、证据和门禁动作；未批准阈值只能标为 `UNAPPROVED`，不能给出达标结论。
- 用例不得依赖执行者的隐含知识；前置条件、数据、步骤和环境必须足够让他人独立执行。
- 需求变化、线上缺陷或版本变化后同步维护用例；保留核心回归集历史，不覆盖来源和版本。

## 输出契约

先给范围结论，再展开细节。根据请求至少提供：

1. 变更摘要、风险等级及依据。
2. 包含项、测试类型、深度、优先级、环境/数据和责任人。
3. 排除项、假设、未知项和重新评估条件。
4. 覆盖矩阵及 `case_priority=CP0/CP1/CP2/CP3`、smoke、regression、security、automation 标签；缺陷严重度仍使用 P0-P4，不能混用。
5. 可执行用例或用例设计方案，包括明确判据。
6. 适用时提供 NFR 来源/批准状态、SLI/SLO、负载/故障模型、环境/工具能力、证据和门禁交接。
7. 用例数、执行轮次、自动化目标、人力/工期估算及假设。
8. 评审状态、未决问题和下一步。

需求不完整时，优先输出覆盖模型和代表性用例，不用大量相似用例制造“完整”的假象。
